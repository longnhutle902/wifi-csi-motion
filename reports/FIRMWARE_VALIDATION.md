# Firmware validation — 2026-11-10

## Scope and changes

Reviewed both ESP32-S3 applications, their Kconfig options, checked-in SDK
configurations, serial output format, CSI callback and queue handling. No boards
were flashed and no experimental data or detection parameters were changed.

- TX was configured for 100 packets/s in both Kconfig and `sdkconfig`, contrary
  to the project's required 50 packets/s. The default and checked-in setting are
  now 50 packets/s; the source comment was corrected too.
- Both checked-in SDK configurations selected the default UART console, whose
  effective baud was 115200 despite the intended 921600 in `sdkconfig.defaults`.
  In the installed IDF's `components/esp_system/Kconfig`, the baud setting is
  configurable only when `ESP_CONSOLE_UART_CUSTOM` is selected. Both projects now
  select that option and generate UART/monitor baud 921600. UART0 and the standard
  ESP32-S3 pins (TX GPIO43, RX GPIO44) are preserved, along with the existing USB
  serial/JTAG secondary console.

The receiver's `STAT,<received>,<dropped>` counters count captured CSI callbacks
and RX queue overflow respectively. They do not independently measure all radio
packet loss. `rx_seq` is the Wi-Fi frame sequence; the TX application payload
sequence is not part of the serial CSI record.

## Reproduction commands

After activating the installed ESP-IDF environment, run the following in each
project directory (`firmware/csi_tx`, then `firmware/csi_rx`):

```powershell
idf.py reconfigure
@'
import json, pathlib, subprocess, sys
entries = json.loads(pathlib.Path('build/compile_commands.json').read_text())
entry = next(x for x in entries
             if x['file'].replace('\\', '/').endswith('/main/main.c'))
result = subprocess.run(entry['command'], cwd=entry['directory'])
print('COMPILER_EXIT_CODE:', result.returncode)
sys.exit(result.returncode)
'@ | python -
```

The compiler initially failed to start inside the Windows sandbox with error
623 (DLL relocation). The same installed compiler ran successfully using
automatically approved execution outside that sandbox.

## Limits

A complete cold `idf.py build` was attempted but interrupted before linking.
It generated more than 1000 build steps per board and was unusually slow on this
machine. Targeting the main archive or object through Ninja also pulled in SDK
dependencies, so the completed source check above invoked the generated compiler
command directly. **A complete firmware link and bootable image are not yet
verified by this record.**

Compilation and generated configuration checks do not verify over-the-air timing,
serial throughput on a physical board, queue behavior under load, or the
experimental detection results. These require a separate hardware run.
